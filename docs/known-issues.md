# 已知问题与限制

> 这份文档的作用：让用的人提前知道哪里会踩坑，而不是踩了才发现。
> 每条都标明**是设计取舍还是缺陷**，以及**有没有计划修**。

---

## 一、能力边界（设计取舍，不打算改）

| 限制 | 为什么这样 | 影响 |
|---|---|---|
| **没有用户鉴权** | 定位是本地单人工具 | **不要直接暴露到公网**，内网部署也要加反向代理鉴权 |
| **单进程单写者** | `Studio` 是唯一状态容器，避免并发写冲突 | 不能水平扩展；重启期间服务不可用 |
| **同一房间一次只做一件任务** | 多条需求交叉会让模型分不清在做什么（UAT 实测过） | 需要并行就开多个房间 |
| **git 只读 + 手动提交** | 成员不能自动 push/merge/amend | 提交需要负责人点确认；diff 不含未跟踪文件 |
| **自定义仓库默认只读** | 防止成员误改你的真实项目 | 要写权限必须显式 `confirm` |
| **沙盒命令白名单只有 node/npm** | 缩小攻击面 | 想跑别的命令得改 `ALLOWED_COMMANDS` |
| **不含内置 MCP server** | 各人需求差异大 | 用 `examples/mcp/` 里的示例或自己接 |

## 二、已知缺陷（会修）

### ✅ stall 判定已修（2026-10-20）

**原来的问题**：任务显示"卡住了"，但成员其实还在工作。UAT 里 20 分钟内撞到两次。

**根因**：判定只看"房间队列空 + 没有正在飞的模型调用"，漏了两种最常见的"慢"：

- 工具正在执行（跑测试可能几十秒）
- 工具在等负责人批准（人可能在开会）

**修法**：抽出 `busyReason()` 纯函数，四条排除条件全部覆盖：

| 条件 | 说明 |
|---|---|
| 房间队列有活 | 自己的 wake 在排队，或别的任务占着 |
| 模型调用进行中 | 推理模型单轮 20~60 秒 |
| 工具正在执行 | `status === "running"` |
| 工具在等审批 | 有 `approvalRequestedAt` 但没有 `approvalDecidedAt` |

**验证**：
- 4 个单元测试覆盖四条条件，并做过反向验证（临时删掉条件后测试确实红）
- 真实模型跑 4 分钟长任务，**0 次误报**（修复前同类型任务至少 1 次）
- 判卡住时会打一条系统消息说明最后观察到的活动，避免"为什么判卡住"无从查证

### ✅ 强制收尾的产物现在会明说「未通过评审」（2026-10-20）

3 轮修订后仍不通过就会强制收尾（`MAX_REVISION_ROUNDS=3`），产物本身可能是半成品。
以前任务卡和正常完成的看起来一模一样，只能自己翻最后一条 review 才能发现。

**修法**：任务卡与任务搜索里显示 `未通过评审` 徽标（依据最后一条 review 的
`verdict === "request_changes"`），悬停提示「产物可能是半成品」。

### 🟡 前端是单文件 app.js（约 10,700 行）

**为什么**：零构建、零依赖是明确的设计目标。

**代价**：改起来要小心，没有模块边界。后续如果继续变大，可能需要拆分或用构建工具。

### ✅ 长任务的消息量已实测（2026-10-20）：真实规模下不构成卡顿

原文档写「超长任务滚动会变慢」，但没有数据。实测（Chromium，406 / 2008 条消息）后修正：

| 规模 | 滚动 | 新消息上屏 | 切回房间（全量重建） |
|---|---|---|---|
| 406 条（约 3 个任务） | 60fps（帧耗 16.6ms） | 136ms（含 120ms SSE 合并窗口） | — |
| 2008 条（远超真实规模） | 60fps（16.6ms） | 每帧约 155ms 长任务 | 274ms |

- 文档描述的真实规模是「一次任务 100+ 条消息」，对应 300 条上下——**这个量级完全流畅**。
- 时间线本来就是增量追加（只在名册变化或消息变少时重建），所以滚动不是瓶颈。
- 极端规模（1500+ 条）下每次状态更新会有约 150ms 长任务；服务端有 `MAX_MESSAGES=1500`
  兜底会裁掉更早的消息，避免 DOM 无限增长。

**结论**：不做虚拟滚动——它会给「零构建」的前端引入一大块状态复杂度，而实测问题不存在。
如果后续要支持「一次会话留存上千条」，先加窗口化渲染（只渲染最近 N 条 + 加载更早），
而不是上虚拟滚动库。

### ✅ 「测试连接通过」不等于「能对话」（2026-10-21）

已经由上面的假阳性条目覆盖：连接测试改为真跑一次对话。这里只补一条经验：
**任何“连通性测试”都必须命中最终要用的那个端点**，否则测的只是 DNS/TLS。

### ✅ 端点偶发返回空内容时不再直接判“解析失败”（2026-10-21）

**现象**：任务显示「模型输出不是可用的 AgentTurn[]（finish=stop, len=0）」，
看不出该改什么。

**根因**：推理模型偶发把整段输出都放进 `reasoning_content`，`content` 返回空串，
`finish_reason` 还是 `stop`。

**修法**：content 为空时自动换非流式重试一次（通常能拿到正常 JSON）；
仍为空才失败，文案直接说明「端点返回了空内容（可能是思考链占满预算或网关抖动）」。

### ✅ 清空过的工作区不会被重启重新播种（2026-10-21）

**现象**：手动清空沙盒后重启服务，演示文件又回来了，真实任务继续被干扰。

**根因**：`ensureSeed()` 以前按「有没有 package.json」判断，空目录会被当成首次启动。

**修法**：清空时写 `.deliverylab-cleared` 标记；`ensureSeed()` 遇到标记直接跳过，
只有「目录不存在」或「空目录且无标记」才播种。`reset()`（界面上的「重置沙盒」）恢复演示内容。

### ✅ 聊天框的短需求不再被漏判（2026-10-21）

**现象**：输入「帮我写一个五子棋的网站」点发送，被当成闲聊，只得到一句客套回复。

**根因**：意图识别规则要求「≥60 字或带列表」，短句一律放行。

**修法**：短句看祈使动词（帮我/写一个/实现/修复/加个…），长段仍看结构信号；
@某人、纯提问（怎么/为什么…）不拦；确认框有样式（见上方「点发送没反应」条目）。

### ✅ 测试连接不再假阳性（2026-10-21，真实用户反馈）

**现象**：设置里「测试连接」显示成功，保存后派活却立刻 `HTTP 400`、任务暂停。
用户合理地质疑：「我不是测试连接通过了吗？」

**根因**：连接测试只请求 `GET /models`——opencode zen 的模型列表**不校验**
`x-opencode-session`，所以返回 200；真正的 `POST /chat/completions` 缺这个头直接
`400 MissingSessionID`。测试测了错端点，等于没测。

**修法**：测试连接改为**真的跑一次最小对话**（`/chat/completions`，max_tokens=8），
带上当前 key 与请求头；失败时给出可操作提示（400 → 提示补 `x-opencode-session`，
401/403 → 检查 key，404 → 检查 Base URL/模型名，429 → 限流）。

### ✅ 只给环境变量里的 key/headers 不再被丢掉（2026-10-21）

**现象**：`LLM_API_KEY=... node src/main.ts`（baseUrl/model 已在设置里）启动后，
`hasKey` 还是 false、请求头为空——key 静默丢失。

**根因**：`readSettings()` 只有在 env 里**同时**有 `LLM_BASE_URL` 与 `LLM_MODEL` 时才构造
llm 配置；只给 key/headers 时整块被丢弃。

**修法**：env 里出现任意一个 LLM_* 就保留，交给 SettingsStore 与 settings.json 合并。

### ✅ 请求头会持久化，重启/重开设置后不丢（2026-10-21）

**现象**：选过 provider 预设（带 `x-opencode-session`），关掉设置面板再打开保存，
请求头就丢了，之后派活 400。

**修法**：额外请求头随 `settings.json` 落盘（权限 0600），值仍**不回传前端**——
接口只暴露 `headerNames`。API key 依然只在内存/环境变量，不落盘。

### ✅ 「点发送没反应」—— 引导弹窗没有样式（2026-10-20，真实用户反馈）

**现象**：在聊天框输入「帮我写一个五子棋的网站」点发送，页面毫无变化。
**根因**：意图识别其实弹了确认框，但 `.confirm-dialog` **没有任何 CSS**——它作为普通块
插在 `<body>` 末尾（top 在视口外），用户完全看不见，主观感受就是「按钮坏了」。
**修法**：补上遮罩 + 居中卡片的样式，并支持 Esc / 点遮罩关闭（文字留在输入框不丢）。

**为什么没被早发现**：当时只断言了 DOM 里有没有这个节点，没看它是否可见——
零构建的前端也一直没有前端测试。已补 `tests/frontend-assets.test.ts`：
`app.js` 语法与体积、关键交互组件类名必须有样式、HTML 标签配平、关键 id 有绑定。

### ✅ Provider 预设与额外请求头（2026-10-20，UX）

**怎么发现的**：真跑时漏传 `x-opencode-session`，opencode zen 每次调用都 400，
而我当时只能靠环境变量补——设置面板里没有入口。

**修法**：设置面板第一屏加 **Provider 预设**（opencode zen / DeepSeek / OpenAI / 本地 Ollama）：
点一下自动填好 Base URL、默认模型和所需请求头，人只需要粘 key；「高级」里也能手填 JSON。
请求头只存进程内存，不落盘、不回传值；「测试连接」会带上它——配错会在测试那一步就暴露。

### ✅ 评审只说话不给结论时，自动补一轮（2026-10-20，真跑发现）

**现象**：reviewing 阶段模型跑了几轮工具、只说话，始终不给 verdict，阶段不推进，
被 stall 判定抓住，看起来像「卡住了」，得人工点半天。

**修法**：评审轮没有 review 结论时，自动补一轮唤醒并在触发器里明确要求
「现在必须输出 `kind:"review"` 与 verdict」；补过仍不给才交给人。同场景有测试覆盖。

### ✅ 长输出与慢模型的两处误判（2026-10-20，真跑发现）

- **思考链吃光预算**：推理模型写长规范时 8192 仍被截断 → 改为阶梯提升
  （4096 → 8192 → 16384 → 32000）后再判失败。
- **回退超时太短**：流被截断后改非流式重试，仍沿用 20s 超时，慢模型必然失败 →
  回退时放宽到 90s。

### ✅ 内置沙盒的演示文件不再干扰真实任务（2026-10-21）

**现象**：默认可写工作区预置了演示用的 `test/export.test.js`、`test/remember.test.js`。
真实任务要求「`node --test` 全绿」时，种子测试混在里面，评审在「整包红 vs 单跑绿」
之间来回拉锯（实测一次任务因此跑了 44 次模型调用、94 次工具仍没收口）。

**修法**：建任务时如果沙盒**仍是未改动的演示种子**，自动清空成空工作区并留一条系统消息；
只要有任何文件被改过就视为真实内容，绝不清空。演示种子只在「重置沙盒」时恢复。


### ✅ 模型失败不再假装成功（2026-10-20）

**产品决定**：只有真实模式——演出不再作为运行时兜底。

**原来的问题**：模型调用失败会退回 mock 台词，任务照常跑完，但负责人**在页面上完全看不见**
产出是假的。实测出现过「11 次调用全失败，任务 30 秒后显示已完成，内容与需求无关」。

**现在的行为**：

| 场景 | 行为 |
|---|---|
| 模型调用失败 | **暂停任务**（`stalled`）+ 落一条系统消息说明原因（HTTP 状态 / 网络错误 / 响应不可解析） |
| 恢复方式 | 恢复面板三选一：继续试试 / 换个方案 / 收尾 |
| 可见性 | 任务卡与搜索显示 `⚠ 调用失败 N` 徽标；任务轨迹保留每次失败的原因 |
| 未配置模型就派活 | `412 llm_unconfigured`，并引导到设置——不会建出假任务 |

### ✅ 「卡住了」的时间提示已修正（2026-10-20）

**原来的问题**：文案把不足 1 分钟强显示成「1 分钟」（`Math.max(1, Math.ceil(...))`），
而且 2 分多钟会显示成「3 分钟」——和实际时间对不上，会误导负责人判断要不要干预。

**修法**：不足 1 分钟按秒说（「已 12 秒」），1 分钟以上按分钟向下取整。

### ✅ 需求没命中剧本时不再「假装懂」（2026-10-20）

**原来的问题**：剧本匹配是零分也取第一个，而且外面完全不知道没命中。于是
「帮我优化一下首页加载速度」会被塞进「记住我」剧本，成员一本正经地讨论 token 过期策略，
跑完还把两条 remember-me 决策写进共享记忆、`sourceTaskId` 指向那条无关需求。
用户的第一反应是「它根本没看懂」，而后续任务会继续被这些假决策带偏。

**修法**：`pickScenario` 返回 `matched`，没命中时给任务打 `scenarioFallback`：

| 行为 | 说明 |
|---|---|
| 演出照常 | 无 key 时总得让人看到点东西，否则一片空白 |
| 任务卡标 `近似演出` | 一眼看出这轮不可信 |
| 首条系统消息 | 说明「台词与决策跟需求无关、不会写进共享记忆」 |
| 不写场景记忆 | 决策/教训一律不落；收尾只写一条诚实的 `fallback-scenario` 教训 |
| 真实模式 prompt | 不再把无关剧本 id 塞进上下文，改为「按需求本身处理」 |

### ✅ SSE 改成合并推送（2026-10-20）

**原来的问题**：每次 `notify()` 都推一帧全量快照。一次状态变更链会连着触发几十次
notify（落消息、改状态位、清草稿），实测 14 秒 39 个事件、共 1.8MB；长任务越跑越卡。

**修法**：连接时仍立即推首帧，之后合并到每 120ms 最多一帧、只发最新状态。
测试覆盖：30 次连续变更必须远少于 30 帧，且最后一帧是最新状态。

### ✅ 提交时挡住敏感文件（2026-10-20）

**原来的问题**：成员有 `write_file` 权限，模型可能顺手在仓库里写出 `.env`、`id_rsa`、
`secrets.json`，而提交一律 `git add -A` —— 这些会被静默写进 git 历史（进了历史删掉也还在）。

**修法**：提交前把敏感路径从暂存区撤下（文件仍留在工作区），并在响应里返回
`skipped` 告诉负责人哪些被挡了。覆盖 `.env` 及其常见变体、`id_rsa*`、`*.pem/*.key/*.p12`、
`.netrc`、`secrets.*`、`.npmrc`；`.env.example` 这类模板不受影响。

### ✅ 降级轮不再污染共享记忆（2026-10-20，API 真跑发现）

**怎么发现的**：API 引擎跑同一个复杂案例时出现 2 次降级（流式响应被提前断开），
降级退回演出台词后，剧本自带的「后台导出 CSV 走异步 / 权限在 service 层再判一次」
被写进了共享记忆——需求明明是修三个 bug。之前只修了「近似剧本」的污染，漏了「降级轮」。

**修法**：本轮若降级，`decision / memory` 里的记忆条目一律不落库（对话保留）；
任务自动摘要里会标注「本任务有 N 次模型降级，产出可能不可信」并打 `degraded` 标签。

### ✅ 流式被提前断开时改用非流式重试（2026-10-20，API 真跑发现）

**现象**：opencode zen 的流式请求偶尔在没有 `finish_reason` 的情况下结束，
JSON 断在半句 → 解析失败 → 整轮降级成演出台词。

**修法**：检测到「流结束但没有 finish_reason」或解析不出 turn 时，**改用非流式重试一次**，
拿到完整回复就不降级；非流式也失败才降级（不会无限重试）。

### ✅ done 阶段是终态，不再派活（2026-10-20，API 真跑发现）

**现象**：评审 approve 后任务卡在 `status=done / stage=working`：approve 时先
`beginStage(done)`、status 仍是 active，架构师在这一轮里又发交接去补 minor，
趁窗口把阶段拉回 working，任务就此卡死。

**修法**：`routeHandoffs` 与交接落库都同时判 `stage === "done"`；done 阶段的派活会被忽略，
文字降级成一条普通消息（内容不丢、但不留一张永远不投递的交接卡）。
prompt 里也补了「done 阶段只做收尾、不要派活」。

### ✅ 真实模式不再被「内部剧本 id」带偏（2026-10-20，真跑发现）

**怎么发现的**：拿 order-service（3 个真 bug + 7 个红测试）在真实模式（CLI 引擎）跑了一遍，
任务修得对（7/7 绿、commit、merge），但模型的产物标题和评语里冒出「导出 CSV v2」
「权限在 service 层兜住了」——需求明明是修三个 bug。

**根因**：prompt 里带了 `场景 id：export_csv`。scenarioId 只是 mock 演出的内部标识，
真实模式完全不需要它，模型却把它当成需求线索开始编。

**修法**：真实模式 prompt 不再透传 scenarioId，只给需求原文和仓库事实；
新增测试断言 prompt 里不出现内部剧本 id（已做反向验证）。

### ✅ 轨迹条目现在能区分「消息」与「产物」（2026-10-20）

真跑时发现轨迹里 `kind: "artifact"` 有两种来源：一条引用产物的消息、以及产物本身，
消息条目没有 `meta`，外部脚本按产物形状读会炸。
现在消息条目统一带 `meta.messageId`，产物条目带 `meta.artifactId`，两者可区分。

### ✅ 产物可以溯源到「哪次模型调用」（2026-10-20）

**原来的缺口**：任务轨迹能回答「时间花在哪」（121 秒里 88 秒是模型思考），但反过来
答不出「这个 patch 是哪次调用写的、当时在评审什么」——产物只有 `kind/title/version/author`，
和模型调用之间没有连线，**可追溯性只做了半件**。

**修法**：产物记录 `trace { stage, llmCallId, trigger }`：

| 位置 | 能力 |
|---|---|
| 产物卡 | 显示「来自 <阶段> · 模型调用」，点「查看来源」 |
| 任务轨迹 | 自动定位并高亮产生它的那次调用（短 id 可对齐）；找不到时提示「已被裁剪」 |
| 轨迹接口 | `artifact.meta.llmCallId` ↔ `llm.meta.id` 可互查，外部集成也能用 |

老数据没有 `trace` 时整行不渲染，不会报错。

### ✅ 成员数量已可配置（2026-10-20）

以前名册写死四只（架构师 / 评审 / 设计 / 实现各一），加人要改代码、改存档也只认原来那些 id。

现在可以在设置面板里直接增删成员：

| 能力 | 说明 |
|---|---|
| 新增成员 | 名字（1–8 字）+ 角色 + 可选人格；自动加入所有房间 |
| 移除成员 | 进 `retiredCats` 存档，历史消息仍显示名字并标「已移除」 |
| 角色约束 | 架构师 / 评审各**只能一个**；设计 / 实现**可以有任意多个** |
| 保留底线 | 名册必须至少有一个架构师、一个评审、一个设计或实现 |
| 移除保护 | 成员手上有未结束的任务时拒绝移除 |

**已不再适用**：产品只有真实模式，成员 roster 由设置决定，新成员会像其他人一样被 @ 和派活。
内置剧本只作为示例素材，不参与运行时。

### ✅ 建房间的错误提示说人话（2026-10-20）

漏传 `workspaceId` 时以前报「workspaceId 不存在」——用户明明没传这个字段，不知道该填什么。
现在区分两种情况：没传报「必填（内置 `ws_sandbox`，或在设置里添加仓库）」，
传了查不到报「不存在：<id>」。

## 三、真实模型相关（provider 特性，不是本项目缺陷）

| 现象 | 原因 | 应对 |
|---|---|---|
| 单任务 5–20 分钟 | 推理型模型思考链长 | 用非推理模型会快很多；或缩小任务粒度 |
| 偶发 `finish_reason: length` | 推理 token 吃光了 completion 预算 | 已内置 4096→8192→16384→32000 阶梯重试 |
| 模型偶尔无视 JSON 约束 | provider 行为 | 已兜底成一条 message，不整轮降级 |
| token 用量差别巨大 | CLI 引擎每次约 20k 起步（CLI 自带系统提示） | 常规任务用 API 引擎 |

**实测数据**（opencode zen · deepseek-v4.1-flash）：
- 一次完整任务：46 次模型调用、322,850 input tokens、20 分钟
- 时间分布：**模型思考占 44–66%**，工具执行占比很小

## 四、已修复的历史问题（记录下来避免回退）

这些都是真实模型/真实用户跑出来的，每个都有测试兜底：

| # | 问题 | 修法 |
|---|---|---|
| 1 | 模型输出被 `max_tokens` 截断后整轮失败 | 阶梯重试到 32000 |
| 2 | JSON 数组后面跟了一段说明文字 | 取第一个 `[` 到最后一个 `]` |
| 3 | 模型返回裸对象 / 多个对象拼接 | 平衡括号切分后包成数组 |
| 4 | 工具名写成 `command` 而不是 `cmd` | 两个都接受 |
| 5 | 工具不在本轮目录时被静默丢弃，整轮降级 | 内置工具保留，交 driver 拒绝 |
| 6 | intake/planning 阶段工具探索死循环 | `MAX_EXPLORE_ROUNDS=1` |
| 7 | 连续工具失败没有上限 | `MAX_CONSECUTIVE_TOOL_FAILURES=3` |
| 8 | 评审↔修订无限拉锯 | `MAX_REVISION_ROUNDS=3` + 强制收尾 |
| 9 | 模型无视 JSON 直接说人话 | prompt 加正反例 + 纯文本兜底成 message |
| 10 | 流式超时 20s 太短，慢模型被 abort | 流式单独放宽到 90s |
| 11 | 模型把参数平铺在顶层而非 `input` 里 | 兼容扁平写法 |
| 12 | 模型自创成员名（"沈砚"→"燕燕"） | prompt 加名字↔catId 对照表 |
| 13 | 聊天框提需求不建任务，但文案说"直接说就行" | 引导弹窗 + 文案修正 |
| 14 | 模型调用进行中被误判"卡住了" | stall 判定排除飞行中的调用 |
| 15 | 审批卡被折叠进历史后找不到 | 待审批浮条常驻 |
| 16 | 房间忙时新需求与在跑任务交叉 | 系统提醒 + `force` 显式放行 |
| 17 | 任务完成但共享记忆为空 | `ensureTaskMemory()` 系统兜底，模型写过则不重复 |
| 18 | 任务 done 后仍派活，stage 回退成 working | `routeHandoffs` 加 done 保护 |
| 19 | 同房间允许并行建多个任务 | 有推进中任务时返回 409 |
| 20 | stall 排队时刷屏「任务暂停推进」 | 排队/思考/工具执行时静默重计时，同任务只提示一次 |
| 21 | 错误码统一 500（房间不存在、请求体过大也是 500） | 404 / 413 / 400 分别返回 |

详细的现象、根因、修法见历史报告：

## 五、排障手册

### 5.1 任务不动了

按这个顺序判断，**不要一上来就干预**：

| 现象 | 说明 | 你该做什么 |
|---|---|---|
| 任务卡显示「等待审批」，有工具卡是 ⏳ | 正常，在等负责人 | 点「批准执行」或「拒绝」 |
| 成员名册显示某个成员「工作中」 | 正常，它在想或跑工具 | 等 |
| 有 `Needs Me` 徽标 | 有东西需要你处理 | 点它跳过去 |
| 显示「卡住了」+ 恢复面板 | 判定确实没有活动 | 看恢复面板给的原因，选继续/换方案/收尾 |
| 30 秒内无变化且无任何标记 | 可能真出问题了 | 看服务端日志 |

**干预按钮的语义**（恢复面板三选一）：

- **继续试试**：解除卡住，让当前 owner 接着推进。适用于"它只是需要再推一把"。
- **换个方案**：可附一句方向（如"别读文件了，直接写结论"），作为新指令注入。
  适用于"方向跑偏了"。
- **收尾**：记录原因 + 写一条教训进共享记忆，任务直接 done。
  适用于"这个任务不值得再投入"。

### 5.2 成员说的话看不懂 / 答非所问

先看两个地方：

1. **任务轨迹**（🔍 查看轨迹）→ 筛选「模型」→ 看有没有「降级」标记。
   降级意味着模型调用失败、退回了 mock 台词——**这时候成员说的都是假的**。
2. **交接卡**五栏是否完整。缺栏会标黄，缺的是「未决问题」时说明它自己也没想清楚。

### 5.3 换了模型之后行为不一样

这是正常的。不同 provider 的 JSON 服从度差异很大，详见
[real-model.md 第 7 节](real-model.md#7-各-provider-实测差异重要)。

最快的调法：把 temperature 降到 0–0.3，能显著提升结构稳定性。

### 5.4 数据会不会丢

- 状态每 200ms 防抖写一次 `data/studio.json`，**原子写入**（tmp + rename），断电不会写坏；
- `data/` 是唯一需要备份的目录；
- API key **不落盘**，重启后需要在设置里重新填（或用环境变量启动）。

详见 [deployment.md](deployment.md) 的「持久化」一节。

## 六、报告问题

如果你踩到上面没列出的问题，请按这个顺序收集信息：

### 最有用的三样东西

1. **任务轨迹**
   页面上点「🔍 查看轨迹」，里面有：每次模型调用的模型名/耗时/token/是否降级原因、
   每次工具调用的状态、每次交接的内容摘要。
   **这是排查的第一手材料**——大部分问题看这个就能定位。

2. **服务端日志里的关键行**

   ```bash
   # 模型层的问题
   grep "\[llm-brain\]" 日志文件

   # 引擎层的问题（阶段推进、审批、stall）
   grep "\[engine\]" 日志文件
   ```

3. **`data/studio.json`**
   完整状态快照。⚠️ 注意里面包含你的需求原文和成员的完整对话，可能含敏感信息，
   **贴到公开的地方前先脱敏**。

### 提交问题时请说明

```
- 用的什么 provider / model（还是 mock 模式）
- 引擎是 API 还是 CLI
- 任务跑到哪个阶段出的问题
- 有没有降级（轨迹里的红色数字）
- 复现步骤（越短越好）
```
