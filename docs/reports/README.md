## 为什么保留这些报告

它们不是"过期文档"，而是三类无法从代码里读出来的信息：

### 1. 踩过的坑

比如「模型输出被 `max_tokens` 截断，整轮直接降级到 mock 台词」这个问题，
代码里只能看到重试逻辑，看不到**它是怎么被发现的**。

报告记录的是：现象 → 复现步骤 → 根因 → 修法 → 回归测试。
后来的人（包括未来的自己）不必重新踩一遍。

### 2. 不同 provider 的差异

同一个机制，在 DeepSeek 和 opencode zen 上的表现不一样：

- DeepSeek `deepseek-flash` 慢但听话；
- opencode zen 的 `mimo-v2.6-flash` 会在 JSON 前后夹 `</think>` 标记、把参数平铺在顶层；
- 换 provider 前读一遍，能少走弯路。

### 3. 性能基线

「一次任务 5 分 52 秒，其中模型思考占 62%，工具只占很小一部分」——
这个数字直接决定了优化方向（减轮数 / 换快模型，而不是优化工具）。

没有这份基线，"要不要优化"只能靠感觉。

## 写新报告的约定

如果要新增测试报告，请遵守：

1. **文件名带日期或在开头明确标注日期**；
2. **开头写清楚测试环境**（provider、model、引擎类型、是否全新数据目录）；
3. **区分「发现了什么」和「现在是什么样」**——后者应该更新到 known-issues；
4. 报告里的数字**标注获取方式**（命令、时间点），方便复现。
