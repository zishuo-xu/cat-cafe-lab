## 二、做得好的地方（实测验证）

### 1. 复杂任务表现优秀

提交了一个五段式需求：

> CSV 导出乱码 + 5 万行卡住两分钟，要求排查根因并修复，1）中文不乱码 2）不阻塞主线程
> 3）给出可复现验证方法。另外顺手把 test 目录里已经失效的用例清掉。

**5 分 52 秒完成，全部验收点都覆盖到了：**

| 需求点 | 猫的处理 |
|---|---|
| 根因 | 宪宪直接指出「乱码=CSV 无 UTF-8 BOM，Excel 按本地编码猜；两分钟卡顿=同步全量拼串」 |
| 中文不乱码 | 补丁里写 BOM，并标注「必须显式参数、默认开启」 |
| 不阻塞主线程 | 加 `toCsvChunks` 流式分块 |
| 验证方法 | 给出 `node --test` 可复现命令 + 逐字节比对 |
| **清死代码** | 砚砚**拒绝执行**：「删 0 条不是偷懒，是没证据不动刀」 |

**特别值得说**：砚砚在评审时不仅放行了补丁，还留了 3 条 minor：

> 内存峰值没解，只解了主线程 —— `toCsvChunks` 入参仍是全量 rows 数组，5 万行能过，
> 百万行照样 OOM。建议接受 async iterable 或明确行数上限。

这是**超出需求表层、指向真实工程风险**的判断。

### 2. 并发提交时模型不乱

同时提交 3 个任务到同一房间，宪宪识别出了重复性：

> 3 号与 1 号、2 号的需求原文完全相同…没有功能点、没有接口位置、没有验收标准。
> **我不会替铲屎官编一个功能出来。**

它拒绝编造，要求澄清。这比"随便编个功能然后跑完"要好得多。

### 3. 可观测性数据完整

一次任务的轨迹：**18 次模型调用、97k input tokens、27 次工具、2 次重试、0 次降级**，
每条都有耗时和 token，能清楚看到钱和时间花在哪。

## 三、发现的问题

### 🔴 P0：任务完成但共享记忆为空

**现象**：任务跑完、评审 `approve`、产出 5 个产物，但「共享记忆」区显示 0 条。

**原因**：记忆依赖模型在 `decision` turn 里主动给 `memory` 字段。这次宪宪的
decision 轮只说了话（「我落成待办单」），没有按格式给 memory，于是什么都没存。

**为什么是 P0**：项目的核心卖点之一是「跨任务的共享记忆」，**它不应该靠模型自觉**。
同类问题会在任何一次模型抽风时复现。

**建议修法**：任务进入 done 时，系统兜底生成一条摘要记忆（至少记录：任务标题、
最终评审结论、产物清单、未清 blocker），不依赖模型输出。

### 🟠 P1：同一房间允许并行多任务

**现象**：并发 POST `/api/tasks` 三个都返回 201，三个任务同时 active 并互相交叉。

**矛盾**：上一轮刚做了「房间忙保护」（有活跃任务时聊天消息会提醒），但**只拦了聊天，
没拦任务创建**。设计意图是「一个房间一次只做一件事」。

**建议修法**：`POST /api/tasks` 在房间已有活跃任务时返回 409，并提示开新房间或等待。
（或者明确允许并行，但要在 UI 上讲清楚，并让任务卡片显示各自的进度。）

### 🟠 P1：stall 提示过于频繁且易误解

**现象**：三个并行任务各自打了一条「任务暂停推进（12000ms 没有任何动作）。最后观察到的活动：排队中。」

**问题**：
1. **措辞矛盾**——「暂停推进」+「最后活动：排队中」读起来像自相矛盾
2. **噪音**——并行任务排队时每个都会打一条，刷屏
3. 实际上这是**正确行为**（确实在排队等），只是表达方式让人困惑

**建议修法**：排队中不判 stalled（直接跳过本轮判定），只有真正没任何活动时才提示。

### 🟡 P2：错误码不规范

| 场景 | 现在 | 应该是 |
|---|---|---|
| 不存在的房间创建任务 | `500 room not found` | `404` |
| 请求体超过上限 | `500 invalid JSON body` | `413` + 明确说"请求体过大" |

### 🟡 P2：创建房间的 `workspaceId` 实际必填但无提示

**现象**：`POST /api/rooms {"name":"x"}` → `400 workspaceId 不存在`。

**问题**：错误信息说"不存在"，但用户根本没传这个字段——应该说「workspaceId 必填」。

## 四、易用性观察

### 好的地方

- **任务进度条 6/6** 一眼就能看出到哪了
- **评审内容可读性高**：blocker/minor 分色，每条带「现象—危害—改法」
- **交接卡五栏完整**：做什么/为什么/取舍/未决问题/下一步
- **轨迹面板**：模型耗时占比做成大数字（62%），一眼看出瓶颈
- **待审批浮条**和**房间忙提示**都正常工作

### 不好的地方

- 三栏信息密度很高，**新用户第一眼容易懵**（虽然有 getting-started 文档）
- 并行任务时，时间线里三个任务的卡片混在一起，**难以分辨哪条属于哪个任务**
- 「任务暂停推进」这类系统消息混在聊天气泡里，**视觉层级不够分明**

## 六、修复情况

本轮测试发现的问题**全部已修**（2026-10-20）：

| 问题 | 修法 | 验证 |
|---|---|---|
| P0 共享记忆为空 | 任务完成时 `ensureTaskMemory()` 兜底写摘要；模型自己写过就不重复 | 单测 2 个 + 真实任务验证 |
| P1 同房间并行任务 | `POST /api/tasks` 在房间有**推进中**任务时返回 409 | 单测 + 实测 |
| P1 stall 排队噪音 | 排队/思考/工具执行时静默重新计时，不判卡住；同一任务只提示一次 | 4 个单测 + 反向验证 |
| P2 错误码不规范 | 房间不存在 404、请求体过大 413、非法 JSON 400 | 4 个单测 + 实测 |
| **P0 新增** 收尾后仍派活 | `routeHandoffs` 在任务 done 后直接返回，避免 stage 回退 | 单测 + 真实任务 |

### 关于「收尾后仍派活」

这是测试过程中**顺带发现的**：一次真实任务先 `done`，之后宪宪还在发交接卡，
导致出现 `stage=working / status=done` 的不一致状态，且新增了一个 `working active` 的步骤。

根因是 `processWake` 有 done 保护，但交接投递在 `afterTurns` 里绕过了它。

**这个问题可能也解释了 P0**：模型想写记忆时，任务已经 done，后续动作被丢弃。
